# Status Update — 2026-07-24

**Editor:** Omprakash Selvaraj (@omscse)

## Summary

Since the last update (2026-06-16), work shifted from spec-only drafting to a real
reference implementation, and this repository's conformance test suite was extended to
match — Goals 2–4 (manifest schema, sandbox, storage) now have draft test cases written
against working code, not just spec placeholders.

## Reference implementation: `portableweb/viewer`

`portableweb/viewer` was rewritten from a standalone desktop app into an npm-workspaces
monorepo (`packages/core`, `packages/store`, `packages/shims`, `packages/electron`), with
61 automated tests passing across those four packages. A working desktop viewer
(Electron-based) was verified end-to-end: it opens the project's own canonical
`hello.pweb` example, isolates each bundle in its own storage/session partition, and denies
every capability except storage (`storage: "isolated"`, the manifest's own default).

Android and iOS got real Capacitor-generated native projects. Android additionally has the
container/manifest/path-resolution logic ported to Java, with 22 passing JVM unit tests and
a real debug APK build — further along than iOS, where the lack of a full local Xcode
install limited work to a scaffold plus one verified native component (a DEFLATE
decompression bridge). Neither mobile platform's viewer is functionally complete yet — the
native project shells exist, but the code that would actually open a `.pweb` file from an
OS "Open With" action hasn't been written on either platform yet.

## Test suite: Goals 2–4 now have draft test cases

Previously, only Goal 1 (container) had test cases; Goals 2–5 were stubs. This update adds:

- **Goal 2 (manifest schema):** 6 test cases — required-field presence/absence, `id`/
  `version`/`entry` shape validation, and the tolerance rule for unknown keys.
- **Goal 3 (sandbox):** 6 test cases — per-bundle storage isolation, popup/navigation
  blocking, permanent service-worker denial, and reserved-path protection at runtime (not
  just at archive-parse time).
- **Goal 4 (storage):** 3 test cases — denial semantics, cross-session persistence, and
  identity-by-`id` (not by filename).

One of these — **`tc-sandbox-002`** — is flagged as a keystone test: it's the one that
validates the conformance model itself (a viewer implementing zero optional capabilities
beyond mandatory baseline behavior is fully conformant, not "partially done"), rather than
one isolated feature. The reference implementation's own fixture corpus treats the
equivalent case the same way.

Goal 5 (inter-bundle communication) remains a stub — no reference implementation exists for
it yet, so no test cases were written against real behavior for it this round.

## Open items surfaced by building the reference implementation

- **Permissions model discrepancy.** This repository's spec draft (`spec/index.html`) uses
  a split `internet.read`/`internet.write` model. The IETF Internet-Draft and the reference
  implementation's actual manifest schema both still use a single boolean `network` field.
  These need reconciling before the capability-schema test cases can go further —
  recommend the split model, since it's more expressive, but this is a call for the group,
  not something resolved unilaterally by the implementation work.
- **CSP requires `'unsafe-inline'`.** Building a real Content-Security-Policy against the
  reference implementation surfaced that this project's own canonical `hello.pweb` example
  bundle uses an inline `<style>` and `<script>` block — a CSP without `'unsafe-inline'`
  would break it, and likely most simple hand-written or AI-generated single-file bundles.
  Worth stating explicitly in the eventual Viewer Conformance section, rather than
  assuming "no inline scripts" the way some earlier informal project notes did.
- **`network` permission scope.** Also surfaced while building the CSP: the `network`
  permission should gate only *external* (non-bundle) destinations. A bundle fetching its
  own packaged resources via `fetch("assets/data.json")` isn't "network access" in the sense
  this permission is meant to gate, and blocking it by default would break a common,
  legitimate pattern.
- **Missing-entry-file behavior undecided.** What a viewer MUST do when `manifest.json`'s
  `entry` is well-formed but the referenced file doesn't exist in the archive — reject
  outright, or render a defined error page — isn't decided yet. Flagged in
  `tests/manifest-schema/tc-005-invalid-entry-path.md`'s notes; needs a decision before a
  corresponding container-level test case can be written.

## Next

- Reconcile the `network`/`internet.read`/`internet.write` permissions-model discrepancy.
- Decide the missing-entry-file behavior (reject vs. defined error page).
- Write the WebView-level glue (scheme handler, storage bridge, document-start injection) to
  make the Android and iOS viewers actually open a `.pweb` file, not just launch.
- Continue filling in Goal 3/4's remaining gaps (CSP content as a tested requirement,
  decompression-bomb/duplicate-filename protections) as the reference implementation grows.
